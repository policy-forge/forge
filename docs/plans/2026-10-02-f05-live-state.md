## Pagination behavior

A table keeps its controls, result region, local status and local error. Navigation
and filters stage the requested cursor/index/filter state; only a current verified
response publishes it. Loading or a failed read retains the previous rows and says
that those rows are previous results. A successful page or filter action focuses
the result region. Inline failures focus their error after the containing view is
no longer inert. Overview's review count selects result-list focus through the
same existing unsaved-edit decision.

The status reads `N matching items of M total · Page n.` Filtered reads obtain M
from an unfiltered one-item read and require the same top-level `resource_version`
as the filtered page. A mismatched version or impossible denominator is an error,
not a count. Typed cursor version conflicts offer a restart from the first page.
Retry repeats the staged read; it does not advance committed state. Local read and
view generation guards prevent superseded replies from replacing rows, announcing
an obsolete error or changing focus. Existing API snapshot/cursor validation
remains authoritative.

The display uses 50 items per page; bounded metadata checks reject unsupported
versions, item counts, totals and cursor shapes. The separate existing full-list
helper retains its 10,000-item display bound. No new total-count estimate or
percentage is derived.

## Operation behavior

A JS-created `#operation-region` lives inside main content outside the replaceable
view and global status. Each session-owned operation keeps one live status, safe
error and actions across navigation. It recognizes the declared preparation kinds
and five states: pending, running, succeeded, failed and cancelled. Unknown kinds,
states, IDs or unusable progress facts remain unverified and expose a known-ID GET
recovery path. Repeated accepted operation observations are deduplicated; automatic status
updates do not move focus.

Optional/null progress is indeterminate. Supplied nonnegative integer facts are
announced as X of Y reported items, without a derived percentage. OpenAPI permits
independent counters; completed greater than total remains a valid observation
with an explicit indeterminate explanation, rather than announcing a reconciled
ratio. Zero of zero is reported as supplied facts.

Cancellation preserves the action node, announces the request separately from
terminal cancellation, and retains an acknowledged request through later polls.
Its generation guard rejects older in-flight observations and failed reads;
invalidated failures continue polling instead of erasing a cancellation acknowledgment. A late cancellation
error cannot replace a newer verified terminal outcome with unknown. Failed or
lost known-ID polling recovers by GET only, never by another preparation POST. An
initial unacknowledged request still uses the same idempotency key on retry; a
structurally unsupported initial ID provides relaunch guidance without a POST
retry. Each polling run allows at most 120 GET attempts with 500 ms spacing; this
is an attempt bound, not a guaranteed wall-clock deadline. Display retention is
bounded at the server's 256-operation session limit. Separately, up to 256 hidden
request slots reserve recovery before an initial effect request. A background POST
failure cannot mutate the destination's global error or focus: its session-owned
request row exposes Retry with the same key and body. Concurrent replay is guarded.
A known operation takes over recovery and releases that request slot. If its Retry
owned focus, that explicit handoff focuses the connected named operation status;
background responses preserve unrelated destination focus. A direct
prepared-preview response after navigation offers local Review without another
POST; hiding the focused Retry hands focus to its named prepared-result status. Request slots are a display bound, not an approved performance budget.

Succeeded preparation offers Review prepared write. Completion in a different
view does not open a preview. An explicit review uses the normal discard decision
and checks the current view/session again after reading the receipt. If a verified
successful preparation's preview read fails, success remains known and Review is
available again. Existing receipt-bound confirmation alone can produce Saved.
Review actions stay focusable while unavailable and catch receipt failures
locally, preserving a newer destination's focus. A successful current Review clears
its previous local error. Shutdown invalidates view generations, observations and receipt reads, disables
operation and request actions
and says status is no longer queryable in that session.
