### F0367 — src/diff/engine.rs:137-138 — `build_summary` — maintainability · low
Root cause: `unchanged` is derived one-sidedly as `total_old.saturating_sub(removed + changed + uuid_changes)`; the caller-supplied `total_old`/`total_new` are trusted and never cross-checked against each other or against the entry buckets, so inconsistent totals produce a plausible-but-wrong `unchanged`. Evidence: `build_summary` (line 122) is the only producer and `diff_artifacts` (src/diff/mod.rs:69) passes `old_controls.len()`/`new_controls.len()`, so the invariant holds today only by caller discipline; `saturating_sub` would silently clamp a stale total. Remediation: after the `unchanged` computation in `build_summary`, add `debug_assert_eq!(unchanged, total_new.saturating_sub(added + changed + uuid_changes))` with a message including both totals, and document the precondition "callers must pass totals consistent with the entry set (`total_new == added + changed + uuid_changes + unchanged`)" on the public `build_summary` doc. No test/snapshot impact (debug-only).

### F0368 — src/diff/engine.rs:15-20 — `compare_controls` — maintainability · low
Root cause: the public crate API takes concrete `&HashMap<String, ControlSnapshot>` (implicitly the default `RandomState` hasher) and suppresses the `clippy::implicit_hasher` lint that exists to flag exactly this; any consumer holding a differently-hashed map or a `BTreeMap` must rebuild a `HashMap` to call a pure function. Evidence: lines 16-20 show `#[allow(clippy::implicit_hasher)]` over the public signature; the body only uses `contains_key`/`get`/iteration. Remediation: remove the allow, make the signature generic `<S: std::hash::BuildHasher>(old_map: &HashMap<String, ControlSnapshot, S>, new_map: &HashMap<String, ControlSnapshot, S>)`; body unchanged. In-crate call sites (src/diff/mod.rs:66) and tests keep compiling. No snapshot impact.
