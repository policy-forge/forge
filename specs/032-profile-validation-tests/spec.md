## User Scenarios & Testing *(mandatory)*

### User Story 1 - Automated Structural Validation of Generated Profiles (Priority: P1)

A developer needs automated confirmation that every Profile generated by `forge profile` is structurally valid OSCAL — not just syntactically correct output. When a generated Profile has incorrect structure, missing required fields, or invalid element placement, the validation suite catches it immediately rather than at the point a downstream tool rejects the file.

**Why this priority**: Structural validity is the most fundamental quality gate for OSCAL output. Without it, generated Profiles may be accepted by FORGE but rejected by downstream GRC platforms, compliance tools, or standards validators. This directly validates the parent PRD acceptance criterion for Profile generation.

**Independent Test**: Generate a Profile from a sample catalog using `forge profile` with a control inclusion list, then run automated structural validation against the OSCAL v1.2.0 Profile standard. Verify validation reports zero structural errors.

**Acceptance Scenarios**:

1. **Given** a valid catalog with multiple controls, **When** generating a Profile with a control inclusion list and running structural validation, **Then** the output passes validation with zero errors.
2. **Given** a valid catalog with multiple controls, **When** generating a Profile with a control exclusion list and running structural validation, **Then** the output passes validation with zero errors.
3. **Given** a valid catalog with controls and parameters, **When** generating a Profile with parameter overrides and running structural validation, **Then** the output — including the parameter tailoring section — passes validation with zero errors.

---

### User Story 2 - Golden-File Regression Tests That Catch Unintended Output Changes (Priority: P1)

A developer needs regression tests that lock down the exact expected output for representative Profile generation scenarios. When any future change to Profile-related code unintentionally alters the output format or content, the golden-file tests immediately fail and require explicit approval before the change is accepted.

**Why this priority**: Without golden-file tests, changes to Profile-related code during upcoming work items could silently alter Profile output in unexpected ways. Golden-file tests are the strongest automated regression safety net for output format stability.

**Independent Test**: Generate Profiles for at least three known scenarios (inclusion-only, exclusion-only, inclusion with parameter overrides) and compare each output against its pre-approved expected output fixture. Verify all comparisons match.

**Acceptance Scenarios**:

1. **Given** a known catalog and control inclusion list, **When** generating a Profile and comparing its output to the pre-approved fixture for that scenario, **Then** the output matches the expected fixture.
2. **Given** a known catalog and parameter override inputs, **When** generating a Profile with parameter tailoring and comparing to the fixture, **Then** the output — including the parameter tailoring section — matches the expected fixture.
3. **Given** an intentional change to the Profile output format, **When** running the golden-file tests, **Then** the tests fail and require explicit fixture approval before passing again.

---

### User Story 3 - Edge Case Tests for Boundary Inputs (Priority: P1)

A developer needs tests that exercise the limits of Profile generation — empty control selection, selecting every control, conflicting parameter overrides, and invalid inputs — to ensure the system behaves predictably under all conditions before the phase milestone release.

**Why this priority**: Edge cases are where subtle bugs hide. Systematically testing boundary conditions before the phase release prevents surprises during integration testing and in production use.

**Independent Test**: Run tests for each boundary condition: empty control selection, all-controls selection, same parameter ID set twice, control ID not in catalog, and duplicate control IDs in the inclusion list. Verify each produces a well-defined, documented outcome — either a valid Profile output or a clear descriptive error message.

**Acceptance Scenarios**:

1. **Given** a catalog with controls, **When** generating a Profile with an empty control inclusion list, **Then** a descriptive error is returned identifying the empty selection — an empty Profile is not produced.
2. **Given** a catalog with 10 controls, **When** generating a Profile that includes all 10 control IDs, **Then** a valid Profile is generated that imports all controls and passes structural validation.
3. **Given** the same parameter ID specified twice with different values, **When** generating a Profile, **Then** the outcome is well-defined: either the last specified value is used or a descriptive error is produced, and the behavior is tested and documented.
4. **Given** a control ID in the inclusion list that does not exist in the source catalog, **When** generating a Profile, **Then** a descriptive error or warning is produced identifying the unknown control ID.

---

### Edge Cases

- What happens when the same control ID appears twice in the inclusion list? The duplicate is handled idempotently — no duplicate import entries are produced in the Profile.
- What happens when both inclusion and exclusion flags are used together? WI-30 treats `--include` and `--exclude` as mutually exclusive — a descriptive error is returned (`"--include and --exclude are mutually exclusive"`) with a non-zero exit code. The test for this case is an error-assertion test, not a golden-file scenario.
- What happens when the catalog file path is invalid or the file does not exist? A descriptive error is produced with a non-zero exit code.
- What happens when the catalog file is not valid OSCAL content (malformed JSON at a valid path)? No error is produced: `build_profile()` uses the catalog path as an OSCAL Profile `href` reference only and does not parse catalog content. Catalog content validation is out of scope for WI-30 and WI-32.
- Do dynamic fields (generated identifiers and timestamps) in Profile output cause golden-file comparisons to fail? No — dynamic fields are normalized to stable placeholder values before comparison, so identical inputs always produce a consistent result.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-000**: The `OscalModelType` enum in `src/validate/mod.rs` MUST be extended with a `Profile` variant; `load_schema()` and `detect_model_type()` MUST be updated accordingly, with `schemas/oscal_profile_schema.json` embedded via `include_str!`. This makes `forge validate` Profile-capable as a natural consequence of reusing WI-19 infrastructure.
- **FR-001**: The validation suite MUST confirm that Profiles generated with control inclusion flags are structurally valid per the OSCAL v1.2.0 Profile standard.
- **FR-002**: The validation suite MUST confirm that Profiles generated with control exclusion flags are structurally valid per the OSCAL v1.2.0 Profile standard.
- **FR-003**: The validation suite MUST confirm that Profiles generated with parameter override flags are structurally valid per the OSCAL v1.2.0 Profile standard, including the parameter tailoring section.
- **FR-004**: The validation suite MUST include golden-file comparison tests for at least three representative scenarios: inclusion-only, exclusion-only, and inclusion with parameter overrides.
- **FR-005**: Golden-file tests MUST use `insta` snapshot testing (consistent with WI-21 Catalog/Component golden files). Dynamic fields (UUIDs, `last-modified` timestamps) MUST be normalized before snapshot comparison using the same UUID/timestamp replacement pattern from `golden_file_tests.rs`. Snapshots are stored in `tests/snapshots/` and updated intentionally via `cargo insta review`.
- **FR-006**: The validation suite MUST include a test covering empty control selection, verifying the outcome is well-defined and either produces a valid Profile or a descriptive error.
- **FR-007**: The validation suite MUST include a test covering all-controls selection, verifying the resulting Profile is structurally valid and imports all controls.
- **FR-008**: The validation suite MUST include a test covering conflicting parameter overrides (same parameter ID specified twice), verifying the outcome is well-defined and documented.
- **FR-009**: All validation, golden-file, and edge case tests MUST be runnable via a single automated test command with no failures.
- **FR-010**: The parent PRD acceptance criterion (generating a valid OSCAL Profile from a catalog with include/exclude flags) MUST be verified by a dedicated end-to-end test that explicitly confirms it passes.

### Key Entities *(include if feature involves data)*

- **Profile**: An OSCAL document generated by `forge profile` that selects and tailors controls from a catalog into a baseline. The subject of all validation, golden-file, and edge case tests.
- **Golden-File Fixture**: A pre-approved `insta` snapshot (`.snap` file in `tests/snapshots/`) representing the canonical normalized output for a specific Profile generation scenario. Updated intentionally via `cargo insta review`.
- **Structural Validation** (also referred to as **Schema Validation** in PRD, AR, and tasks.md — both terms are synonymous in this feature): The process of confirming that a generated Profile document conforms to the OSCAL v1.2.0 Profile structural standard, catching missing fields, incorrect nesting, and invalid element placement.
- **Dynamic Field Normalization**: The process of replacing generated identifiers and timestamps in Profile output with stable placeholder values before golden-file comparison, enabling consistent comparison across runs.
- **Edge Case**: A boundary condition or unusual input (empty selection, all controls, conflicting overrides, invalid catalog) used to verify predictable behavior at the limits of Profile generation.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Every Profile generation path (inclusion, exclusion, parameter tailoring) has automated structural validity confirmation — zero generation paths are unvalidated.
- **SC-002**: At least three golden-file scenarios are established and passing, providing regression coverage for the three primary Profile generation modes.
- **SC-003**: At least three boundary conditions (empty selection, all-controls selection, conflicting overrides) are tested and produce documented, well-defined outcomes.
- **SC-004**: The parent PRD acceptance criterion for Profile generation is verified by a dedicated end-to-end test that passes with zero failures.
- **SC-005**: Golden-file comparisons produce consistent results across repeated runs with identical inputs — zero spurious failures from dynamic field variation.
- **SC-006**: Any unintended change to Profile output format is detected automatically — the golden-file test for the affected scenario fails until the fixture is explicitly updated.

## Assumptions

- Profile generation (control inclusion/exclusion) and parameter tailoring (parameter override flags and the modify section) are complete and their existing tests are passing before this validation work begins. Any build errors introduced by subsequent WIs (e.g., WI-34 adding required fields to `PolicyRequirement`) must be resolved as a prerequisite before WI-32 implementation begins — fixing such errors is explicitly out of WI-32 scope.
- The OSCAL v1.2.0 Profile structural standard is stable and available as a validation reference.
- Schema validation infrastructure already proven for Catalog output (from prior work) can be extended for Profile output without rebuilding it from scratch.
- Golden-file test infrastructure already proven for Catalog and Component output (including dynamic field normalization) can be extended for Profile output without rebuilding it.
- Fixture files use normalized placeholder values for generated identifiers and timestamps, so comparisons are stable across repeated runs.
- Edge cases that reveal bugs in Profile generation or parameter tailoring are documented and tracked separately; known failures may be recorded as expected during this sprint if the fix belongs to a prior work item.
- Tests use synthetic catalog data — not real organizational policy content.
- This is a test-only work item. No new Profile generation features or CLI flags are introduced.
