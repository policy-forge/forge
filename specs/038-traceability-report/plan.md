# Implementation Plan: Traceability Report

**Branch**: `038-traceability-report` | **Date**: 2026-03-10 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/038-traceability-report/spec.md`

## Summary

Implement the `forge trace` subcommand that reads an OSCAL artifact (Catalog or Component Definition JSON), extracts WI-17 trace metadata (props/links), resolves source locations against the original policy file, and produces a column-aligned text table mapping every OSCAL element to its source policy location. The report includes coverage statistics (mapped/unmapped/total) and a staleness heuristic comparing source file mtime against OSCAL `metadata.last-modified`.

## Key Design Decisions

### D-1: Read OSCAL artifacts as serde_json::Value (not typed structs)

The `forge trace` command reads arbitrary OSCAL artifact JSON files from disk. Unlike the conversion pipeline (which builds typed Catalog/CompDef structs from PolicyDocument), the trace command consumes pre-existing JSON files that may have been generated by any OSCAL tool. Using `serde_json::Value` for parsing allows walking arbitrary JSON structures without coupling to specific struct versions. The extractor looks for trace props by namespace + name convention.

**Rationale**: Catalog JSON on disk has an envelope `{"catalog": {...}}` and CompDef has `{"component-definition": {...}}`. The typed structs (`OscalCatalog`, `ComponentDefinition`) are builders — they produce OSCAL, they don't consume it from arbitrary JSON. Using `serde_json::Value` is simpler and more robust for reading.

### D-2: Source staleness via mtime comparison (not hash)

WI-17 does not embed a source file hash. The staleness heuristic compares the source file's filesystem modification time against the OSCAL artifact's `metadata.last-modified` ISO 8601 timestamp. This is imperfect (mtime can be reset) but provides a useful signal without requiring WI-17 changes.

### D-3: Groups shown with partial data

WI-17 embeds `source-section` on groups but not `source-file` or `source-line`. Groups appear as report rows with section populated and line shown as "—". They count as mapped if they have a `source-section` prop.

### D-4: Parts excluded from report

WI-17 does not embed trace metadata on parts. Parts are excluded from the element walk to avoid inflating the unmapped count.

### D-5: Column layout (4 columns)

Per clarification, the Source Paragraph column is dropped. Table columns:
`OSCAL Element ID | Element Type | Source Section | Source Line`

### D-6: Trace prop extraction by namespace + name

Extract trace metadata by matching `ns == FORGE_TRACE_NS` and `name == PROP_SOURCE_*`. Import constants from `src/oscal/trace_embedding.rs` to stay in sync with WI-17.
