# Feature Specification: OSCAL Component Definition Structure

**Feature Branch**: `014-component-definition-structure`
**Created**: 2026-02-12
**Status**: Draft
**Input**: User description: "OSCAL component definition structure -- components and capabilities that describe what a product or service offers for control satisfaction"

## User Scenarios & Testing *(mandatory)*

### User Story 1 -- Generate Component Definition Structure (Priority: P1)

A developer or compliance engineer converts a policy document and needs the outer Component Definition JSON structure with a documentary component representing the policy. This is the foundational artifact for the component-first conversion strategy (`--strategy component`), which represents a security policy as a documentary component that "implements" controls from an external baseline.

**Why this priority**: This is the structural foundation for the entire component-first strategy. WI-15 (implemented-requirements), WI-16 (traceability), and WI-18 (end-to-end pipeline) all depend on it. It directly enables Parent PRD M-4 and US-2.

**Independent Test**: Given a PolicyDocument with title "Corporate Security Policy" and version "2.0", build a Component Definition and verify the JSON contains a `component-definition` root with correct metadata and a `components` array with one documentary component of type `"policy"`.

**Acceptance Scenarios**:

1. **Given** a PolicyDocument with title and version, **When** building a Component Definition, **Then** the output JSON has a `component-definition` root object with `uuid`, `metadata.title`, `metadata.last-modified`, `metadata.version`, and `metadata.oscal-version` fields correctly populated. *(AC-1, AC-2; traces to M-1, M-2)*
2. **Given** a PolicyDocument, **When** building a Component Definition, **Then** the `components` array contains exactly one entry with `type: "policy"`, a valid UUID, and `title`/`description` derived from the PolicyDocument. *(AC-3, AC-5; traces to M-3, M-5, M-6)*
3. **Given** the same PolicyDocument built twice, **When** comparing component UUIDs, **Then** both runs produce the same component UUID. *(AC-4; traces to M-4)*

---

### User Story 2 -- Reuse Metadata Assembly Pattern (Priority: P1)

The Component Definition must use the same metadata assembly logic as the Catalog builder to ensure consistency across all OSCAL artifacts generated by FORGE.

**Why this priority**: Consistency across artifacts prevents bugs and reduces maintenance. The metadata pattern (WI-11) is already proven for Catalog generation.

**Independent Test**: Build both a Catalog and a Component Definition from the same PolicyDocument and verify their metadata blocks are structurally identical (same fields, same `oscal-version`, same derivation of title/version).

**Acceptance Scenarios**:

1. **Given** the same PolicyDocument, **When** generating both a Catalog and a Component Definition, **Then** both artifacts have structurally consistent `metadata` blocks with the same `oscal-version` value of `"1.2.0"` and matching title/version derivation. *(AC-6; traces to M-7)*
2. **Given** a PolicyDocument with no version, **When** generating a Component Definition, **Then** `metadata.version` defaults to `"0.0.0"` (consistent with Catalog behavior). *(traces to M-2, M-7)*

---

### Edge Cases

- **EC-1** (M-5): When the PolicyDocument has no title (empty string), the component title defaults to `"Untitled Policy Document"`.
- **EC-2** (M-2): When the PolicyDocument has no version, `metadata.version` defaults to `"0.0.0"`.
- **EC-3** (M-3): When the PolicyDocument has no sections or requirements, the Component Definition is still produced with one documentary component (empty content is valid at this structural stage).
- **EC-4** (M-4): When the PolicyDocument's title or version changes, the component UUID changes (deterministic generation from document identity fields).
- **EC-5** (M-1): The output JSON is parseable and the root key is exactly `"component-definition"` (hyphenated, per OSCAL convention).

## Requirements *(mandatory)*

### Functional Requirements

**Must Have (M) -- MVP, launch blockers:**

- **FR-001 (M-1)**: The builder MUST produce a JSON object with root key `"component-definition"` conforming to the OSCAL Component Definition model structure. *(Traces to: Parent PRD M-4)*
- **FR-002 (M-2)**: The Component Definition MUST include required OSCAL metadata: a document-level unique identifier, `title`, `last-modified` timestamp, `version`, and `oscal-version` set to `"1.2.0"`. *(Traces to: Parent PRD M-4, M-5)*
- **FR-003 (M-3)**: The `components` array MUST contain one documentary component with `type: "policy"`. *(Traces to: Parent PRD M-4)*
- **FR-004 (M-4)**: The documentary component MUST have a stable, deterministic identifier (UUID v5) generated from the PolicyDocument's title and version, such that the same title and version always produce the same identifier. *(Traces to: Parent PRD M-4, M-8)*
- **FR-005 (M-5)**: The documentary component `title` MUST be derived from the PolicyDocument's title. When the PolicyDocument has no title, it defaults to `"Untitled Policy Document"`. *(Traces to: Parent PRD M-4)*
- **FR-006 (M-6)**: The documentary component `description` MUST use the template format `"Documentary component representing the {title} policy document."` where `{title}` is the PolicyDocument's title (or the default title if empty). *(Traces to: Parent PRD M-4)*
- **FR-007 (M-7)**: The builder MUST reuse the metadata assembly pattern established in the Catalog builder (WI-11) for generating the document-level metadata block. *(Traces to: consistency with WI-11)*

**Should Have (S) -- High value, not blocking:**

- **FR-008 (S-1)**: The builder SHOULD include an empty `control-implementations` array on the documentary component as a placeholder for WI-15.
- **FR-009 (S-2)**: The builder SHOULD include back matter resources (reusing WI-12 logic) when the PolicyDocument contains citations.

**Could Have (C) -- Nice to have, if time permits:**

- **FR-010 (C-1)**: The documentary component COULD include properties for document-level metadata (e.g., source document version from PolicyDocument version).

**Won't Have (W) -- Explicitly deferred:**

- **W-1**: `implemented-requirements` population -- *Deferred to WI-15*
- **W-2**: Source profile reference in `control-implementations[].source` -- *Deferred to WI-15*
- **W-3**: Traceability props/links on component elements -- *Deferred to WI-16/WI-17*
- **W-4**: Schema validation of generated Component Definition -- *Deferred to WI-19*
- **W-5**: End-to-end CLI wiring (`--strategy component`) -- *Deferred to WI-18*
- **W-6**: Multiple documentary components per Component Definition -- *Single policy = single component for now; multi-component is a future extension*

### Key Entities

- **Component Definition**: The top-level OSCAL artifact describing how controls are implemented by reusable components. Contains a unique document identifier, metadata, a components array, and optional back matter.
- **Documentary Component**: A component within the Component Definition of type `"policy"` representing a non-technical control implementation (the security policy itself). Has a deterministic identifier, title, description, and a placeholder for control implementations.
- **OSCAL Metadata**: The required metadata block present in every OSCAL document -- title, last-modified timestamp, version, and OSCAL version (`"1.2.0"`).
- **PolicyDocument**: The internal domain model representing a parsed policy document (from WI-5). Serves as the input source for all derived Component Definition fields.
- **Back Matter**: Optional section containing resources referenced by the document (reused from WI-12), included when the PolicyDocument contains citations.

## Clarifications

### Session 2026-02-12

- Q: What content should be hashed for the documentary component's UUID v5? → A: Title + version only (document identity fields); requirement-level changes are captured by control-level UUIDs in WI-15.
- Q: Should the PRD glossary "Component UUID" be corrected from UUID v4 to UUID v5? → A: Yes, correct to UUID v5 to align with all requirements and architectural decisions.
- Q: What strategy should the builder use for the documentary component's description field? → A: Always use the template format: "Documentary component representing the {title} policy document." for consistency.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Given any valid PolicyDocument, the builder produces a well-formed Component Definition JSON with the correct root key and all required metadata fields populated (5 of 5: identifier, title, last-modified, version, oscal-version). *(Traces to: M-1, M-2)*
- **SC-002**: The `components` array contains exactly one documentary component of type `"policy"` with a non-empty title and description derived from the PolicyDocument. *(Traces to: M-3, M-5, M-6)*
- **SC-003**: The documentary component identifier is deterministic -- identical PolicyDocument content produces identical component identifiers across repeated builds. *(Traces to: M-4)*
- **SC-004**: Metadata blocks generated for Component Definitions are structurally consistent with those generated for Catalogs from the same PolicyDocument, confirming pattern reuse. *(Traces to: M-7)*
- **SC-005**: Test coverage for the Component Definition builder exceeds 90%. *(Traces to: technical verification)*
- **SC-006**: All edge cases (EC-1 through EC-5) are covered by tests and pass successfully.

### Assumptions

- [A-1] The Catalog builder pattern (WI-9 through WI-13) is complete and provides a reusable metadata assembly function.
- [A-2] The Component Definition at this stage contains exactly one documentary component (one policy document = one component). Multi-component definitions are a future extension.
- [A-3] The `control-implementations` array will be empty or absent at this stage -- WI-15 populates it.
- [A-4] Back matter assembly (WI-12) can be reused for the Component Definition without modification.
- [A-5] OSCAL v1.2.0 Component Definition JSON structure is stable and well-documented.
