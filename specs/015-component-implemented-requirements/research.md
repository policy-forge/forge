# Research: Component Implemented Requirements (WI-15)

## R1: Control-ID Generation Strategy for Implemented Requirements

**Decision**: Reuse the Catalog builder's control-id scheme by walking sections and calling existing public utility functions.

**Rationale**: The OSCAL `control-id` field in `implemented-requirement` references the `id` of a control from the source profile/catalog. In FORGE's Catalog (WI-9), controls have IDs like `POL-AC-001` generated by `generate_control_id(abbreviation, requirement_index, "POL")`. For cross-artifact consistency, the Component builder must produce identical control-ids for the same requirements.

**Alternatives Considered**:
- **Use stable_id (UUID) as control-id**: Rejected — stable_id is a UUID (e.g., `550e8400-...`), not a human-readable control identifier. OSCAL `control-id` must reference the Catalog control's `id` field.
- **AR's `control_id_from_stable_id` pass-through**: The AR proposed a simple function that returns stable_id as-is. This is insufficient because stable_id is a UUID, not a control-id. The Component builder needs section-aware ID generation.
- **Pre-compute and store control-ids on PolicyRequirement**: Would require modifying the domain model (WI-5) and pipeline. Over-engineers for a single consumer.

**Implementation Approach**:
1. The `build_control_implementations` function receives `&PolicyDocument` (not `&[PolicyRequirement]`), giving it section context.
2. It walks `document.sections` depth-first (same order as Catalog builder).
3. For each section, calls `generate_section_abbreviation` and handles abbreviation collision resolution (same logic as Catalog's `resolve_abbreviation`).
4. For each requirement in a section, calls `generate_control_id(abbreviation, req_idx, "POL")`.
5. Make `resolve_abbreviation` from `catalog.rs` accessible as `pub(crate)` — minimal visibility change, no API change.
6. Fallback for missing stable_id (EC-2): use `REQ-{zero-padded index}` where index is the global requirement index across all sections.

**Validation**: A unit test will generate both a Catalog and a Component Definition from the same PolicyDocument and verify all control-ids match.

## R2: UUID v5 Namespace Constants for WI-15

**Decision**: Derive two new namespace constants from `FORGE_NAMESPACE_UUID` using the established pattern.

**Rationale**: Each OSCAL element type uses its own UUID v5 namespace to prevent collisions. WI-7 established `FORGE_NAMESPACE_UUID`, WI-12 added `BACK_MATTER_NAMESPACE`, WI-14 added `COMPONENT_NAMESPACE`. WI-15 needs two new namespaces.

**Constants**:
- `CONTROL_IMPL_NAMESPACE`: Derived from `Uuid::new_v5(&FORGE_NAMESPACE_UUID, b"control-implementation")`
- `IMPL_REQ_NAMESPACE`: Derived from `Uuid::new_v5(&FORGE_NAMESPACE_UUID, b"implemented-requirement")`

**Derivation Process**: Compute the UUID v5 values, then store as hardcoded byte arrays (same pattern as existing constants). Compute once via a test or script:
```rust
let ci = Uuid::new_v5(&FORGE_NAMESPACE_UUID, b"control-implementation");
let ir = Uuid::new_v5(&FORGE_NAMESPACE_UUID, b"implemented-requirement");
```

**UUID Seed Content**:
- Control-implementation UUID: `format!("{source_profile}\0{policy_title}")` (deterministic per baseline+document)
- Implemented-requirement UUID: `format!("{stable_id}\0{text}\0{index}")` (deterministic per requirement; index ensures uniqueness for EC-5 — identical text with different positions)

**Alternatives Considered**:
- Single namespace for both: Rejected — different element types should use distinct namespaces per WI-7 convention.
- Include source_profile in implemented-requirement UUID seed: Rejected — the requirement's identity doesn't change with the baseline; only its grouping does.

## R3: `build_component_definition` Signature Change

**Decision**: Add `source_profile: Option<&str>` parameter to `build_component_definition`.

**Rationale**: The Component Definition builder needs the source profile reference to populate `control-implementations[].source`. The Catalog builder doesn't need it (no source profile concept). Making it `Option<&str>` allows:
- `None` when called without source profile (existing WI-14 tests pass unchanged with `None`)
- `Some(profile)` when called with `--source-profile` from the component pipeline

**Impact on Existing Tests**: All existing tests for `build_component_definition` currently call with just `&PolicyDocument`. They will pass `None` for `source_profile`, maintaining backward compatibility. The function only generates control-implementations when `source_profile` is `Some`.

**Alternative Considered**:
- New function `build_component_definition_with_controls`: Rejected — adds API surface; a single function with an optional param is simpler.

## R4: Component Pipeline Wiring

**Decision**: Create `run_component_pipeline` in `pipeline.rs`, mirroring `run_catalog_pipeline`.

**Rationale**: The component pipeline shares stages 1-7b (ingest through citation extraction) with the catalog pipeline. Only Stage 8+ diverges: build component definition instead of catalog. Duplicating the shared stages is acceptable for now (pipeline refactoring to share stages is a future WI concern).

**Pipeline Stages**:
1. Ingest file (reuse)
2. Reconstruct content (reuse)
3. Validate non-empty (reuse)
4. Extract sections (reuse)
5. Extract clauses (reuse)
6. Assemble document (reuse)
7. Atomize document (reuse)
8. Assign stable IDs (reuse)
9. Extract citations (reuse)
10. Build component definition with source_profile
11. Serialize to JSON
12. Write output

## R5: `--source-profile` CLI Integration

**Decision**: Add `--source-profile` as an `Option<String>` field on `Commands::Convert`, validated at runtime.

**Rationale**: `--source-profile` is only required for `--strategy component`. Making it optional at the clap level and validating at runtime (in `convert.rs`) produces a clear, context-specific error message rather than a generic clap error.

**Validation Rules** (from FR-009, SEC-3, SEC-4, EC-4):
- If `strategy == Component` and `source_profile` is `None` -> error: `--source-profile is required when using --strategy component`
- If `strategy == Component` and `source_profile` is `Some("")` (empty string) -> error: `--source-profile must not be empty`
- If `strategy == Catalog`, `source_profile` is ignored (no error if provided)

**Alternative Considered**:
- Use clap's `requires_if` for conditional requirement: Rejected — clap error messages are generic; runtime validation produces a more descriptive, actionable error.
