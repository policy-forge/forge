**Branch**: `035-prd-phase2-release` | **Date**: 2026-02-19 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/035-prd-phase2-release/spec.md`

---

## Summary

WI-35 is a pure integration testing and release sprint. All Phase 2 features (WI-26–WI-34) are implemented and unit-tested. This plan adds cross-cutting integration tests that verify Phase 2 capabilities work together, confirms no Phase 1 regressions, then prepares and tags the `v0.2.0` release. The selected approach (AR Option 1) extends the WI-25 (Phase 1 release) pattern: modular integration test files, standard `cargo test` framework, reuse of existing round-trip and golden-file infrastructure, three-gate quality check before tagging.

## Implementation Plan

### Phase 1: Write Integration Tests (Days 1–3)

**Priority order follows PRD priority: P1 stories first.**

#### Step 1.1 — Round-Trip Integration Tests

File: `tests/integration_round_trip.rs`

Write 4 test functions that exercise the `forge export` CLI end-to-end (subprocess via `env!("CARGO_BIN_EXE_forge")`):

| Test | PRD Req | Coverage |
|------|---------|----------|
| `catalog_json_xml_json_round_trip` | M-1 | Catalog JSON→XML→JSON semantic equivalence |
| `catalog_json_yaml_json_round_trip` | M-1 | Catalog JSON→YAML→JSON semantic equivalence |
| `component_definition_json_xml_json_round_trip` | M-1, EC-5 | CompDef JSON→XML→JSON |
| `component_definition_json_yaml_json_round_trip` | M-1, EC-5 | CompDef JSON→YAML→JSON |

**Approach**: (1) `forge convert` → JSON file, (2) `forge export` → XML/YAML, (3) `forge export` → JSON back, (4) `serde_json::Value` deserialized comparison for semantic equivalence. Reuse `tests/common/mod.rs` forge helper pattern.

#### Step 1.2 — Profile End-to-End Integration Tests

File: `tests/integration_profile_e2e.rs`

Write 5 test functions covering the complete Profile generation → validation pipeline:

| Test | PRD Req | Coverage |
|------|---------|----------|
| `profile_include_produces_valid_oscal` | M-2 | --include → imports[].include-controls |
| `profile_exclude_produces_valid_oscal` | S-1 | --exclude → imports[].exclude-controls |
| `profile_set_param_produces_modify_section` | M-3 | --set-param → modify.set-parameters |
| `profile_passes_schema_validation` | M-4 | forge validate on generated Profile |
| `profile_xml_yaml_formats` | S-2 | Profile in XML and YAML formats |

**Approach**: Use `tests/fixtures/golden/` fixtures as Catalog inputs. Generate Profiles via `forge profile` subprocess. Parse output JSON for structural assertions. Validate via `forge validate` subprocess.

#### Step 1.3 — Cross-Feature Integration Tests

File: `tests/integration_cross_feature.rs`

Write 6 test functions verifying Phase 2 cross-cutting properties survive format conversion:

| Test | PRD Req | Coverage |
|------|---------|----------|
| `normative_props_present_in_json` | M-5 | `prop[name="modality"]` in JSON output |
| `normative_props_survive_xml_round_trip` | M-5, AC-8 | prop preserved after JSON→XML→JSON |
| `normative_props_survive_yaml_round_trip` | M-5, AC-8 | prop preserved after JSON→YAML→JSON |
| `param_elements_present_in_json` | M-5, AC-7 | `param` elements in JSON output |
| `param_elements_survive_xml_round_trip` | M-5, AC-8 | params preserved after JSON→XML→JSON |
| `param_elements_survive_yaml_round_trip` | M-5, AC-8 | params preserved after JSON→YAML→JSON |

**Approach**: Use a synthetic policy fixture containing both normative ("must") and advisory ("should") language plus parameterized requirements ("within 90 days"). Convert to JSON, assert props/params present. Convert to XML and back; assert props/params identical. Repeat for YAML.

#### Step 1.4 — Regression Integration Tests

File: `tests/integration_regression.rs`

Write 3 test functions confirming Phase 1 baseline is preserved:

| Test | PRD Req | Coverage |
|------|---------|----------|
| `phase1_catalog_structure_regression` | M-6 | Catalog golden-file comparison (additive diffs allowed) |
| `phase1_component_structure_regression` | M-6 | Component Definition golden-file comparison |
| `phase1_validate_still_passes` | M-6 | forge validate on existing Phase 1 golden artifacts |

**Approach**: Load existing golden fixtures from `tests/fixtures/golden/`. Convert via CLI. Compare structure — assert core fields (uuid, metadata, groups/controls, components) match expected values. For `prop` and `param` additions from Phase 2, allow their presence but do not assert their absence (additive changes expected).

## Anti-patterns to Avoid

- **DO NOT** write new feature code — this sprint is integration testing and release only.
- **DO NOT** tag v0.2.0 until ALL three quality gates pass (`cargo test`, `cargo clippy -- -D warnings`, `cargo fmt --check`).
- **DO NOT** skip regression testing — Phase 1 functionality must be explicitly verified.
- **DO NOT** test only JSON output — XML and YAML must each be explicitly tested.
- **DO NOT** hard-code test expectations to specific serialization ordering — use `serde_json::Value` deserialized comparison for semantic equivalence.
- **DO NOT** update Phase 1 golden files unless a Phase 2 additive change is expected and documented.
